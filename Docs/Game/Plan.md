## Phases
Each phase ends with compile, EditMode tests green, notes and index updated, a `--no-ff` merge into `develop`.

0. **Setup**: project, Core port, docs, skills.
1. **Scope and decisions** (with the developer): settle the open decisions below; download the supplied assets into `Assets/Art/` and review them (problems found go to the README feedback section); write the first entries in [Decisions](Decisions.md); create the four game assemblies and the test assembly.
2. **Data and logic** (`Game.Data`, `Game.Logic`): level format (board size, blocks with shape and color, doors with side, position, width and color, timer), board state, moves and collisions, exits through a matching door, win when the board is empty, fail when the timer reaches zero, coin wallet rules. EditMode tests first.
3. **Level editor** (`Game.Editor`): an editor window that draws the board; set width and height, paint blocks, place doors on the edges, set the timer; create, open, save, play from the editor; undo. Show the `LevelValidator` report (errors stop saving, warnings are shown). A test that every color id in the level assets has a material in the palette. Author the 5 levels with it (own designs, 4 x 5 to 5 x 6, two to six blocks; `Level_01` made again in the editor). Usability check: make a level from scratch without reading code. Agreed design:
   - **Window**: an `EditorWindow` drawing the board from above in 2D, UI Toolkit only (UXML, USS, C#), no IMGUI inside; if UI Toolkit blocks something, the whole window moves to IMGUI. Start with a spike the developer tries before the rest is built.
   - **Working copy**: the window edits a in-memory ScriptableObject copy (`DontSave`), undo works on it; Save validates and writes it into the `LevelAsset`, so a level with errors is never saved; `hasUnsavedChanges` asks on close. Update the "levels as ScriptableObjects" decision, which promises undo on the asset itself.
   - **Tools** as strategies (`Press`, `Drag`, `Release`, preview) looked up once, no switch: Select/Move (select a block or door, change its color, delete, drag to move), Block (one drag makes one block; a drag starting on a block extends it), Door (press on the edge strip and drag along it for the length), Erase. Edit operations in a plain class with EditMode tests; the window draws and forwards input. Shortcuts through `[Shortcut]`: tools by letter, colors 1-9.
   - **Validator additions**: `DoorsOverlap` and `DisconnectedBlock` errors. Shrinking the board removes the block cells and doors that fall outside in one undo step.
   - **Levels**: New creates the next `Level_NN` asset and appends it to the `LevelCatalog`; open from a dropdown of the catalog or by double-clicking a level asset; order in the catalog's inspector.
   - **Play from the editor**: saves, writes the level into `SessionState` and enters play mode; the game starts that level directly. Until the Boot scene exists it opens `Game.unity`; from phase 5 Boot reads the same request and skips Home (Boot stays loaded but unseen, so app-wide services are the real ones).
   - **Problems panel**: errors and warnings listed, a click highlights the block, door or cell; Save disabled with the reason while there are errors.
   - **Scene preview**: with the Game scene open, the level open in the editor (live), else the level asset selected in the Project window, is built in the scene by the game's `BoardBuilder` as unsaved, non-editable objects; removed in play mode.
   - **Solver** (`Game.Logic`, engine-free, tests first), using the board's own step rules: moves are reversible and an exit only frees cells, so a level cannot be made unsolvable by the player and exiting a block as soon as it can is always safe; the search rearranges blocks (any cell a block can reach through free cells is one move) only when no block can exit. Gives an `Unsolvable` warning, the minimum move count and a solution the editor can play back step by step. A state budget keeps it bounded and reports "unknown" when exceeded. Its metrics (moves, rearrangement moves, dependency depth, blocks free at start) are the generator's input later.
4. **Gameplay** (`Game`): board and block views, drag input, door views, slide and exit animations, HUD (timer, coins, level number), pause with resume, restart, home; fail popup (restart, home); win then next level; coins saved through Core.Save. Visual notes from the spike, in order of weight:
   - a white outline on the held block, as in the reference;
   - camera framed to each level's size, checked at 1080 x 1920 and 20:9, and the lighting tuned;
   - after the snap and hold, the door breaks the block apart piece by piece: each quarter piece that crosses the door line is hidden and a pooled particle burst plays in its place (measure timing from a recording of the reference);
   - the door lowers while a block passes and rises again (if time allows).
   - one place in the session reacts to the attempt's outcome the first time it leaves `Playing`, for win and fail alike: `Won` is set inside `MoveTo`, `Failed` inside `Tick`, and `Tick` returns the outcome as it stands, not whether it changed.
   - board input through the EventSystem, done with the HUD: a `PhysicsRaycaster` on the camera and one `BoardInputView` on a board-sized collider (sized per level by the builder) with pointer down, drag and up handlers, no drag threshold, the first pointer only; drag positions still projected onto the touch plane. Replaces the polling `BoardPointer`, so HUD buttons and popups block the board.
   - board pieces (block quarters, walls, doors, ground) as prefabs from Core's `PrefabPool`, one pool per piece type in the Game scene's scope, prewarmed when the scene opens: restart and the next level take pieces from the pools and give them back, so a level is built without `Instantiate`. Not in the Boot scope, where pieces would outlive the scene that parents them. The builder takes its pieces from a source the caller gives, so the level editor's scene preview keeps building plain unsaved objects without pools. With it, the builder stops owning the board's lifetime (today it destroys the last root at the next `Build`, while the preview destroys the same object): `Build` builds into the parent it is given and the caller (the session, the preview) creates and releases it. When per-level camera framing is added, layout, build and framing become one runtime method that the session and the preview both call, so the preview keeps matching the game.
5. **Meta screens**: home (top UI with coins and lives placeholder, level button, settings button, placeholder tab bar, touch feedback), settings (sound, music, vibration toggles bound to Core.Audio and Core.Haptics, close). Check layout at 1080 x 1920 and 20:9.
6. **Delivery**: Android build (IL2CPP, ARM64), a short recording of the full flow, README written from `Decisions.md`, `WorkLog.md` and the known issues, final pass for dead code and style.
7. **Optional, only if 1-6 are complete**: a level generator in the editor (generate and test with a seeded `System.Random`: validator, solver, then difficulty bands from the solver's metrics; Easy, Medium and Hard profiles in a settings asset calibrated on the 5 levels; "similar to this level"; the result goes into the working copy for the designer to adjust), with static HTML reports from batch mode for tuning it (no HTML editor, no level-generation skill); the out-of-time offer, the first thing that spends coins (more seconds for coins: `CoinWallet.TrySpend`, `LevelTimer.AddSeconds`, an out-of-time state in `LevelAttempt` before `Failed`, a popup and a settings asset for price and seconds); then one optional mechanic.

## Risks
- The editor is the second most weighted criterion; budget real time for its usability, not only for its function.
- The live `unity command` bridge does not work on 2022.3; every editor action is a batch-mode run or an editor script, and batch mode cannot open the project while the editor has it open.
- The supplied models need per-file rotations and an own color set ([Supplied assets](SuppliedAssets.md)); budget phase 4 time for the block builder from quarter pieces.
