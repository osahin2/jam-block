# Level editor

> Summary: An editor window where a designer makes and changes levels by drawing on a top-down board. It edits a working copy of a level, so undo covers every change and only a level without errors is written back to its asset. Built in phase 3; this note grows with it.

## Code
- Folder: `Assets/Game/Editor/LevelEditor/` (`Editing/`, `Window/`, `Preview/`, `Levels/`, `Play/`)
- Assembly: `Game.Editor`
- Entry points: `LevelEditorWindow` (`Window/LevelEditorWindow.cs`), opened from the menu **Game > Level Editor** or by double-clicking a level asset.

## How it works
- **Window.** UI Toolkit only: layout in `LevelEditorWindow.uxml`, style in `LevelEditorWindow.uss`, code in `LevelEditorWindow.cs`. A toolbar with a Levels toggle that shows or hides the level list (shortcut L; hidden, the board gets its room, and the state is kept across reloads), the name of the level being edited, New, Duplicate, Save, Play, Revert and an unsaved-changes mark; on the left the level list; a side panel with the tools, the colors of the `ColorPalette` and the board fields; the board; a status line; the problem list under it. Thin handles right of the level list and of the side panel and one above the area under the board can be dragged to resize them (`PaneResizer`, a pointer manipulator), between a minimum and a maximum in the window's code; the sizes are serialized fields of the window, so they survive reloads. The side panel scrolls when the window is short.
- **Open level.** `LevelDocument` is the level open in the window: a level asset, a new level without an asset yet, or none. It owns the working copy and decides what saving, unsaved changes and Revert mean, as plain code with EditMode tests; the window keeps it in a serialized field and adds the dialogs and the views. With no level open, every toolbar button but New is disabled.
- **Working copy.** `LevelDraft` is an in-memory ScriptableObject (`DontSave`; not `HideAndDontSave`, whose `NotEditable` makes bound fields refuse edits) holding a copy of the opened level. Every change goes into it, and `LevelDraft` records it for Unity's `Undo`. Save validates the copy and, without errors, writes it into the `LevelAsset` and saves the asset; Save is disabled while there are errors. The document compares the copy with the asset (a new level with an empty level) for `hasUnsavedChanges`, so closing it or opening another level asks first; every way of opening a level (the level list, New, Duplicate, double-clicking an asset, Revert) goes through one `Load`. Opening the level already open loads it again from its asset, which is what Revert does.
- **Levels.** `LevelLibrary` is the game's `LevelCatalog` as the editor sees it. `LevelListPanel` (its own element, like the problem list) shows the catalog's levels in play order with the open one selected; it is rebuilt when the catalog changes, also from outside (a save, the catalog's inspector). A search field filters by play number or by a part of the name in any case (`LevelSearch`). The list is a `ListView`, which draws only the rows on screen, so thousands of levels stay quick. A click opens a level, a press and release in about one place, so starting a drag to reorder opens nothing (the list selects a row as soon as it is pressed, so opening does not follow the selection); clicking the open one does nothing, where reopening would revert it, and the selection always goes back to the level that is open, also when the designer chose to keep editing; dragging a row changes the play order (`LevelLibrary.Move`), only while every entry is shown, in catalog order; the right-click menu opens, duplicates, shows in the Project window or deletes a level. Delete asks first; `LevelLibrary.Delete` takes the level out of the catalog, leaving no empty entry, and moves its file to the trash, so a level deleted by mistake can be brought back from there; deleting the open level leaves nothing open and clears the scene preview. An entry whose asset was deleted outside the editor shows as a missing level that can only be removed from the list. New opens an empty board (the `LevelData` defaults) under the next name, shown as "Level_NN (new)"; it has no asset yet, so Revert is off; it counts as unsaved once something is on its board, so leaving an untouched one asks nothing. Its first save, without errors, creates `Level_NN.asset` next to the catalog's last level, so moving the levels' folder needs no change in code (in the catalog's own folder while it lists none; the number is the one after the catalog's last level, skipping a name a file already has, checked without loading the asset; names are labels only, the catalog decides the play order, so they are not renumbered after a delete) and appends it to the catalog, so a level with errors never reaches the game and a New that is never saved leaves nothing behind. Duplicate starts a new level the same way from a copy of the open level as it is in the window, unsaved changes included, and asks nothing, since nothing is lost (from the list, another level is copied as saved); its first save adds it as the catalog's next level and the original keeps what was last saved. A level opened by double-clicking an asset outside the catalog is edited and saved as usual, but stays out of the game until it is added to the catalog.
- **Play.** Play saves the level, so the game plays it as it is in the window, and is disabled with Save while the level has errors. While the game is already playing, while scripts have compile errors or with no scene in the Build Settings it shows the reason in the window and writes nothing, so a refused play leaves no request behind. `LevelPlayStarter` hands the level to the game through `EditorPlayRequest` (in `Game`, the asset's GUID in `SessionState`, which outlives the domain reload of entering play mode) and enters play mode. Play mode always starts from the Boot scene, the first enabled scene of the Build Settings, which Core.Scenes keeps as `EditorSceneManager.playModeStartScene`, so the scenes open in the editor stay open and come back when play mode ends. Boot sees the request and opens the Game scene instead of Home; the game takes the request once (`GameEntry`), so a later Play starts the game as usual.
- **Board.** `LevelBoardView` draws the board from above: empty cells as tiles on a dark ground, blocks filling their cells whole in their palette color with a thick edge where the neighbour is not the same block, so each block reads as one piece. Around it a light wall a half cell thick, with the corners closed, shows the doors in their colors. It turns the pointer into cells from -1 to the board's size, so the whole ring cell around the board is addressable for doors, and reports a fast drag cell by cell, so a stroke has no gaps.
- **Tools.** Each tool is an `ILevelEditorTool` (`Describe`, what a press at a cell would do; `Press` and `Drag`, returning whether the level changed, false for a press that changes only the tool's own state such as the selection; `Release`); the window keeps a list of them and forwards the board's pointer cells to the selected one, with no switch over kinds. The changes themselves are in `LevelEdits`, plain code without the engine.
  - `SelectTool`: a press picks the block or door under it; dragging moves it (a block only onto free board cells, a door only along its side and off other doors). With a selection, clicking a color recolors it and Delete removes it.
  - `BlockTool`: one drag draws one block in the chosen color; a drag that starts on a block extends it.
  - `DoorTool`: a press on the frame places a one-cell door in the chosen color, dragging along the side makes it longer; a drag that starts on a door moves its nearer end, so it can be made longer or shorter. Corners take no door.
  - `EraseTool`: erases block cells under the stroke (a block left without cells is removed; one cut in two is reported by the validator) and whole doors.
- **Selections.** A selected block or door is an `ILevelSelection` (`BlockSelection`, `DoorSelection`): each knows its cells, how it moves, recolors and is deleted, so the select tool and the window treat both alike. A selection holds the block or door object itself, not its index, so removing an earlier block or door never makes it mean another one; it is dropped when its object is no longer in the level, and after undo or redo, which may restore the level as new objects.
- **Shortcuts.** `LevelEditorShortcuts` declares them with `[Shortcut]` in the window's context, so they work while the window has focus and can be rebound in Unity's Shortcuts window under "Level Editor": S, B, D, E for the tools, 1 to 9 for the colors (`ColorKeyCount`; a larger palette's other colors are picked with the mouse), Backspace to delete the selection, L to show or hide the level list. The tool buttons show the current keys in their labels and each color swatch has its key written on it; a tool's shortcut is found by the tool's name, which a test checks. They do nothing while text is typed into a field, a number field or the level search.
- **Feedback.** The selected tool is a highlighted button and the selected color is enlarged and named. The board highlights the cell under the pointer, or the whole block or door when it is on one, outlines the selection (the board draws `BoardMark`s, a cell and a style, over the level, so selection and problems use one path), and the line under the board says what the selected tool would do there (its tooltip when the pointer is off the board). The status line has a fixed height and the problem list fills the rest of the area under the board, so the board keeps its size while their text changes.
- **Problems.** The validator runs after every change. `LevelProblemGuide` turns each `LevelProblem` into a sentence a designer understands and into the block or door it is about (an `ILevelSelection`, found by the problem's `LevelPart`; none for a problem with the whole level). The list under the board (`LevelProblemList`, its own element with `FocusChanged` and `Picked` events) has one row per problem: severity, the color and size of its block or door, and the sentence, with a count and "Fix the errors to save" above it. On the board every problem's block or door is outlined and tinted red for an error or orange for a warning, and the cell at fault (an overlap, a cell outside the board) is filled stronger. Hovering a row marks its block or door white; clicking it switches to the Select tool with that block or door selected. Hovering a marked cell on the board adds the problem's sentence to the status line.
- **Undo.** `LevelDraft` records whole copies of the level (`RegisterCompleteObjectUndo`), not differences: Unity's difference-based `RecordObject` restored a list wrongly once a cell was removed from its middle (a block came back with a cell twice). A pointer stroke is one undo step: the draft keeps the level as it was on press and, on release, records it only if the stroke changed something, so an empty click adds no step. Single edits (recolor, delete, resize) record before they change. Undo, redo and the bound time field change the copy outside the tools; `TrackSerializedObjectValue` on the copy redraws the window then.
- **Board fields.** Width and height are delayed fields, applied on Enter or when focus leaves, so typing "10" never resizes to 1 on the way; they go through `LevelEdits.Resize`, which drops the block cells and doors that fall outside a smaller board (one undo step). The time field is bound to the copy.
- **Scene preview.** With the Game scene open (found by its `GameScope`), the level is also built in the scene by the game's own `BoardBuilder` under "Level Preview (not saved)", so the Scene view and the Game view show it as the game will. `LevelScenePreview` builds and clears it; its objects are `DontSave | NotEditable`, so the scene is never dirtied or saved with them and the level is changed only in the window. `LevelPreviewSource`, an `[InitializeOnLoad]` hook, picks the level: the window's working copy while a level is open there (redrawn at most once per editor update, and only when the level differs from the one on show), else the level asset last selected in the Project window. It removes the preview when play mode starts, where the game builds the level itself, and before a script reload, and builds it again afterwards and when a scene opens. A level with a color missing from the palette is not built.
- **Reloads.** The open asset, the copy, the color and the tool are serialized fields of the window, so a script reload rebuilds the window (`CreateGUI`) with the same level and its undo history. The copy is never saved, so after the editor restarts the window has its asset but not the copy, and loads the level again from the asset; unsaved changes are lost with the editor, as in any unsaved asset.

## Rules & invariants
- What a valid level is lives only in `LevelValidator`; the editor shows its report and refuses to save errors.
- The window draws and forwards input; edits are in `LevelEdits` and the tools, which are tested without a window.
- No IMGUI inside the window (decision in [Decisions](../Decisions.md)); the 2022.3 limits of UI Toolkit are in skill `add-game-feature`.

## Known gaps
- The solver, which would warn about an unsolvable level, is optional scope and comes in phase 7.

## Tests
- `Tests/LevelEditor/LevelEditsTests`: adding and finding a block, growing only by a free touching cell, resizing drops what falls outside and keeps the rest.
- `Tests/LevelEditor/BlockToolTests`: a stroke draws one block, a stroke from a block extends it, a stroke from outside the board does nothing, a new stroke makes a new block.
- `Tests/LevelEditor/LevelEditsDoorAndMoveTests`: ring sides and corners, finding doors and their cells, adding and resizing doors without overlap, moving blocks onto free cells only, erasing cells.
- `Tests/LevelEditor/SelectToolTests`: selecting and moving a block and a door, stopping at another block, a selection that keeps its block when an earlier one is removed, clearing, recoloring and deleting.
- `Tests/LevelEditor/LevelEditorShortcutsTests`: every tool, color key, Delete and the level list toggle has a registered shortcut.
- `Tests/LevelEditor/DoorAndEraseToolTests`: placing and lengthening a door, no door on corners or the board, dragging a door's end, stopping at another door, erasing cells and doors.
- `Tests/LevelEditor/LevelProblemGuideTests`: every problem kind has a sentence; a problem's subject is its block or door, none for the whole level.
- `Tests/LevelEditor/LevelScenePreviewTests` (opens `Game.unity` additively; skipped when it is already open in the editor): the preview is built in the Game scene with every object `DontSave` and the scene left clean; a new level replaces the old; clearing removes it.
- `Tests/LevelEditor/LevelLibraryTests` (creates assets in a folder of its own, removed after each test): a new level is saved under the next name and appended to the catalog in play order, next to the last level after the levels were moved and past an entry left empty by a deleted asset; a name a file already has is skipped; the catalog is saved; moving changes the play order; deleting leaves no empty entry and moves the file to the trash (one small test asset per run), and only takes out an entry whose asset was deleted.
- `Tests/LevelEditor/LevelSearchTests`: an empty query matches every level, a part of the name in any case, the play number, spaces around the query ignored, no match.
- `Tests/LevelEditor/LevelDocumentTests` (saves into its own folder and catalog): nothing open has nothing to save; a new level opens empty under the next name, is unsaved only once changed and never revertable; with errors it creates no asset, without errors it becomes the catalog's next level; without a library it is not saved; an open level reverts by opening it again and saves into its own asset; a duplicate starts as a new level with the open level's content as in the window and saves as a level of its own, leaving the original as it was saved; with nothing open there is nothing to duplicate; unloading leaves nothing open.
- `Tests/Levels/EditorPlayRequestTests`: a requested level is taken once, also by another instance, as after a domain reload.
- Entering play mode cannot run in EditMode tests; Play is checked by hand.
- The window itself is checked by hand in the editor; batch mode does not draw windows.
